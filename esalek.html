CASE STUDY

Eysalak

Hybrid POS & Fiscal Electronic Receipt System FinTech Native Android Integration

Esalek is a smart Android-based Point of Sale (POS) application developed in strategic partnership with Fawry, designed to operate on dedicated payment terminals such as PAX A960 and PAX A930, while also supporting standard Android phones and tablets.

The application combines sales processing, shift management, electronic card payments, thermal receipt printing, and integration with the Egyptian Tax Authority (ETA) electronic receipt system in a single platform.

By combining payment processing and fiscal receipt generation, Esalek provides merchants with a unified solution that simplifies daily operations and reduces their dependency on multiple separate devices and systems.

PROBLEM

The Problem

Traditional retail payment environments often require merchants to operate multiple disconnected systems: a POS application for sales, a separate payment terminal for card transactions, and an additional system for fiscal receipt integration.

This creates several operational and technical challenges:

Disconnected Systems

Merchants need to manage sales, electronic payments, and tax-compliant receipts across separate devices and platforms.

Payment and Fiscal Sequence Integrity

Generating a fiscal receipt before confirming a successful card payment can create financial discrepancies and unnecessary fiscal cancellation procedures.

Uncertain Payment Outcomes

Network interruptions or application crashes can leave a transaction in an unknown state, even when the customer’s card has already been charged.

Hardware Dependency

Applications built specifically for payment terminals cannot easily operate on standard Android devices that lack proprietary payment and printing hardware.

CHALLENGES

Key Engineering Challenges & Solutions

1

Payment Processing & Fiscal Receipt Integrity

Challenge

The application needed to coordinate two independent processes: electronic card payment and fiscal receipt generation.

Generating a fiscal receipt before confirming the payment could result in a registered receipt for a transaction that was never successfully paid.

Solution

I implemented an order-first, receipt-after-payment workflow that separates the transaction into distinct stages:

  1. Create a pending order with a unique orderNumber.
  2. Initiate the card payment through the Fawry POS SDK.
  3. Receive the payment result and submit the transaction details to the backend.
  4. Generate the fiscal receipt through the /generate-receipt endpoint only after successful payment confirmation.

This ensures that fiscal receipt generation follows the confirmed payment outcome rather than preceding it.

2

Handling Interrupted & Uncertain Payment Transactions

Challenge

A particularly critical scenario occurs when a customer’s card is successfully charged, but the application fails to receive or transmit the payment confirmation because of a network interruption, device shutdown, or unexpected application termination.

In this situation, the payment may have succeeded while the corresponding order remains pending.

Solution

I implemented a transaction recovery workflow directly within the Transaction Details screen:

  • Preserve pending transactions and their unique orderNumber instead of automatically discarding them.
  • Provide a Fawry Inquiry operation to retrieve the actual payment status using the orderNumber or Fawry reference number (FCRN).
  • Allow the cashier to execute a Void operation when the payment was successful but the transaction should not proceed to fiscal receipt generation.

This gives cashiers a way to investigate and resolve uncertain payment outcomes directly from the POS application.

3

Native Android Integration & SDK Compatibility

Challenge

The Fawry POS SDK exposes functionality through native Android libraries and IPC mechanisms. Integrating these capabilities into a React Native application required a reliable bridge between the JavaScript layer and native Android services.

Solution

I developed a dedicated native module, FawryPaymentModule, responsible for:

  • Managing communication with the Fawry payment service through IPC.
  • Handling Android context and UI-thread requirements.
  • Managing terminal connection and initialization.
  • Supporting automatic connection and local terminal configuration.

This created a dedicated integration layer between the React Native application and the native payment infrastructure.

4

Supporting Dedicated POS Terminals & Standard Android Devices

Challenge

The application needed to run on specialized PAX terminals and ordinary Android phones and tablets.

Directly initializing proprietary PAX printer classes or payment services on unsupported devices could result in runtime errors such as ClassNotFoundException and NoClassDefFoundError.

Solution

I separated hardware-specific functionality from the main application workflow through optional native integrations and feature-based availability checks.

  • Detect the availability of required hardware drivers before initializing native components.
  • Isolate PAX-specific integrations behind dedicated native modules.
  • Provide alternative workflows for devices without specialized payment hardware.
  • Support cash transactions, digital receipt sharing, and standard printing alternatives on compatible Android devices.

This enabled a shared application codebase to support different Android hardware environments without making proprietary hardware a mandatory dependency.

5

Thermal Printing & Arabic Text Rendering

Challenge

Thermal POS printers do not always provide native support for properly shaping and connecting Arabic characters. Printing Arabic receipts directly could result in disconnected characters and incorrect text direction.

Solution

I developed a dedicated PAXPrinterModule for direct communication with PAX thermal printers.

The implementation includes a custom Arabic text-processing component, ArabicManager, to handle Arabic character shaping and RTL text rendering before printing.

The module also supports fiscal QR code printing, while standard Android devices can use alternative printing and PDF generation workflows.
