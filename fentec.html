CASE STUDY

Fentec Mobility

Smart Urban Mobility Platform IoT Integration FinTech

Fentec Mobility is a smart urban transportation platform that enables users to rent electric scooters for short-distance trips. By scanning a QR code on a scooter, users can automatically unlock the device through IoT integration, start their journey, and pay based on their usage.

The platform aims to provide a convenient, affordable, and environmentally friendly alternative to traditional transportation, helping reduce urban congestion while making short-distance travel faster and more accessible.

CHALLENGES

Key Engineering Challenges & Solutions

1

Trip Tracking, IoT Communication & Geofencing

A core part of the platform was coordinating active scooter trips with device communication and geographical restrictions.

The backend was responsible for communicating with scooter IoT APIs throughout active trips, periodically fetching device and location updates through background jobs. It also handled remote device commands, including locking and unlocking scooters when trips started or ended.

To enforce geographical restrictions and ensure safe scooter operation, I implemented a polygon-based geofencing system with three zone types, each triggering different device behaviors:

Green Zones — Approved Areas

Users can ride freely without geographical restrictions.

Orange Zones — Restricted Areas

When a scooter enters an orange zone, the system triggers a speed reduction and starts a grace period, allowing the user time to return to an approved green zone before further restrictions are applied.

Red Zones — Prohibited Areas

When a scooter enters a red zone, it is stopped immediately, and notifications are sent to both the user and responsible administrators to report the violation.

Frequent location updates and polygon calculations introduced performance challenges. To reduce unnecessary database access and repeated geographical calculations, I used Redis to cache relevant coordinates surrounding active trips and nearby zone data.

This required coordinating three components: Google Maps geographical data, scooter IoT APIs, and backend business logic.

2

Third-Party Integrations & Background Processing

The platform relied on multiple external services, including:

  • Scooter IoT APIs for device control and tracking.
  • Google Maps for geographical services.
  • Firebase for push notifications.
  • Apple Developer services and Google services for mobile application integrations.
  • Email services for system communications.

A key engineering challenge was managing these integrations without allowing external service latency to negatively affect the user experience.

I designed integration workflows and evaluated which operations required synchronous execution and which could be delegated to background jobs.

For example, periodic scooter communication and trip tracking were handled asynchronously through background jobs, while time-sensitive device operations such as locking, unlocking, and zone-based speed control were initiated through backend API integrations.

This separation helped maintain responsive user-facing operations while handling external service communication.

3

Financial Transactions & Concurrent Wallet Operations

The platform introduced a points-based wallet system, which required careful handling of concurrent financial operations.

Users could purchase points through a distributed POS network, addressing the challenges of operating in a cash-heavy market such as Algeria. The POS application allowed local merchants to sell points to users in a way similar to mobile phone credit top-ups.

A major challenge was maintaining balance integrity when multiple financial operations affected the same wallet simultaneously. For example, a user could purchase points while on an active trip or receive points from another user at the same time.

To prevent conflicting balance updates, I implemented optimistic locking using a version column combined with database transactions.

Each balance update validated the wallet’s current version before committing changes. When a concurrent update caused a version conflict, the operation performed a single retry: reloading the latest wallet balance and version, recalculating the transaction, and attempting the update again.

Wallet update flow

  1. Validate the wallet’s current version
  2. Version conflict from a concurrent update
  3. Reload latest balance and version
  4. Recalculate the transaction
  5. Attempt the update again

Transaction records were also maintained alongside wallet balances to provide a reliable financial reference and preserve transaction history.
